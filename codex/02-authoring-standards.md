# 02. 작성 표준 (절대 규칙)

> 이 규칙은 `k8scert/CLAUDE.md` §4·§5 를 옮긴 것이다. **위반하면 작업은 반려된다.** 충돌 시 CLAUDE.md 가 최종 기준이다.

## §1. 실습 출력 — 무조건 "실제 터미널 스크린샷 이미지"

- 명령 실행 결과(상태·로그·describe·이벤트·표)는 **실제 터미널 화면을 캡처한 PNG 이미지**로 넣는다.
- **금지되는 출력 표기 3종**(전부 §1 위반):
  1. ` ```text ` 코드블록에 출력 텍스트 붙여넣기
  2. 언어 태그 없는 빈 ` ``` ` 코드블록에 출력 붙여넣기 (`예상 출력:` / `기대 출력:` 라벨 뒤)
  3. ` ```bash ` 블록 안에 출력을 **인라인 주석**으로 적기 (`# 출력:`, `# 기대:`, `# ca.crt namespace token` 등)
- 캡처 방법: 실제 tart 클러스터에서 명령을 **진짜 실행**한 터미널 화면을 캡처 → `k8scert/<자격증>/images/`(또는 `daily/images/`)에 저장 → `![설명](images/파일.png)` 으로 삽입. 헬퍼: `scripts/capture-shot.sh`(05 문서 참조).
- **생성·렌더링 금지**: 터미널처럼 그린 가짜 이미지(Pillow 등)·HTML 캡처·합성 금지. 오직 실제 화면 캡처만.
- **명령 자체**는 ` ```bash ` 로 보여줘도 된다(입력만 보여주는 치트시트·자동완성도 OK). **단 출력은 이미지로.**
- 클러스터가 꺼져 캡처가 불가능하거나 환경에서 재현이 안 되면, **지어내지 말고** "(미캡처)" 또는 정직한 "예시(참조)" 노트로 명시한다.
- 캡션은 정확히 무엇을 보여주는지 적는다(예: "_실제 터미널 캡처 — etcd snapshot status_").

**출력 블록을 이미지로 교체하는 표준 패턴:**
```
(before)
예상 출력:
​```
NAME      STATUS
foo       Running
​```

(after)
**검증 - 기대 출력:** <한 줄 해석. 무엇을 확인하는지>(클러스터 실측, 값은 환경별 상이).
![<무엇을 보여주는 캡처인지>](images/<cert>-<순번>-<설명>.png)
```

## §2. 다이어그램 — mermaid 흑백이 표준

- 개념·아키텍처·흐름·관계 그림은 **반드시 mermaid**. **ASCII 박스 다이어그램 금지**(한글 더블폭으로 테두리 깨짐). 예외: 디렉터리 트리·표는 ASCII 허용(그림이 아님).
- 모든 mermaid 블록 첫 줄에 **흑백 테마 지시자** 필수:
  ```
  %%{init:{'theme':'base','themeVariables':{'primaryColor':'#ffffff','primaryBorderColor':'#000000','primaryTextColor':'#000000','lineColor':'#000000','fontFamily':'Georgia, serif'}}}%%
  ```
- 무채색만(흰 배경·검은 선·검은 글자). **색으로 의미 구분 금지** — 형태(`[]`/`()`/`[()]`/`{}`)·라벨·선 종류(실선/점선)로 구분. `classDef`/`style ... fill:#색` 금지.
- 그림 바로 아래 **번호·캡션** `_그림 N. 제목._` 을 붙인다. 노드 라벨 줄바꿈은 `\n`. 이모지·장식 금지.

## §3. kubectl·YAML (실기 핵심)

- **시험은 속도전**: 명령형(imperative) 풀이 우선 — `kubectl run/create/expose` + `--dry-run=client -o yaml > x.yaml` 패턴을 기본으로. 첫머리에 `alias k=kubectl`, `export do='--dry-run=client -o yaml'` 셋업 안내.
- **YAML 들여쓰기는 공백만(탭 금지).** 매니페스트는 실제 `kubectl apply`(가능하면 `--dry-run=server`)로 검증한 것만 싣는다.
- **컨텍스트·네임스페이스 항상 명시**: 문서 명령에 대상 클러스터(`--context` 또는 `--kubeconfig`)와 `-n <namespace>` 를 명시한다. 실기 문제는 문제마다 `kubectl config use-context <ctx>` 로 전환.
- 매니페스트 예제가 참조하는 **선행 리소스**(ConfigMap·Secret·SA 등)는 그 생성 명령을 같은 문서에 먼저 둔다(없으면 학생이 `apply` 시 실패).

## §4. 독자 = 학부 3~4학년. "이 책만 읽고 자격증을 딴다"가 기준

- **검토 기준**: 컴퓨터공학 3~4학년이 *사전지식 없이* 이 문서만 읽고 ⓐ개념 이해 ⓑ실습 재현 ⓒ자격증 취득이 가능한가? 못 하면 미완성이다.
- **스토리라인 4요소 필수** — 모든 기술 주제는 "그냥 이렇게 한다"가 아니라 **왜 이게 나왔는지의 이야기**로:
  1. **등장 배경** — 이 기술이 없던 시절 무엇이 문제였나(구체적 고통).
  2. **이전 기술과의 차이** — 직전 해결책(예: kube-proxy iptables, docker, PSP, ABAC)의 한계.
  3. **무엇이 나아졌나** — 새 기술이 그 한계를 *어떻게* 넘었나(메커니즘 수준).
  4. **트레이드오프** — 새로 생긴 비용·제약·주의점.
- **쉬운 이해 우선**: 어려운 개념은 ⓐ한 문장 직관 → ⓑ정확한 정의 → ⓒ내부 동작 순. **용어는 첫 등장 시 한 줄 풀이**(예: "RBAC(Role-Based Access Control, 역할 기반 접근 제어)"). 큰 그림(흑백 다이어그램) 먼저, 디테일 나중.
- **흐름의 연속성**: daily N 은 daily N-1 의 무엇을 전제하는지, 이 주제가 자격증 도메인 어디에 속하는지 첫머리에 한 줄. 고립된 토막 지식 금지.

## §5. 문체 규약

1. **문체는 "~이다/한다/된다" 평서체.** 경어체("~합니다/해요") 금지.
2. **공학적 표현만.** "강력한", "마법처럼", "핵심 열쇠" 등 문학적·마케팅 표현 금지.
3. **깊이 확보.** 표면 설명 금지 — 내부 동작 메커니즘, 커널/OS 레벨 원리, 장애 시나리오, 트러블슈팅 포함.
4. **실습 검증 필수.** 모든 개념/예제에 검증 명령 + 실제 터미널 스크린샷(§1).
5. **등장 배경 + 스토리라인 명시**(§4).
6. **학부 3~4학년 가독성**(§4). 작성 후 그 관점으로 재검토.

## §6. 일별(daily) 문서 양식

```
# <자격증> Day N: <제목>
> 학습 목표 | 도메인: <영역> (비중 %) | 예상 소요 시간
> (전제 학습 연결 한 줄: day N-1 의 무엇을 전제하는가)
## 오늘의 학습 목표 (체크리스트)
## 1. <소주제>
   ### 등장 배경·스토리   (4요소, §4)
   ### 개념·내부 동작     (구조·메커니즘 + 흑백 다이어그램, 용어 첫 등장 풀이)
   ### 실측 검증         (실제 kubectl ```bash + 실제 터미널 스크린샷 이미지 + 해석, §1)
   ### 🛠 직접 해보기     (시험형 미니랩, 시간 제약 의식)
   ### 트러블슈팅        (흔한 실패 + 원인 + 복구 명령)
## ✅ 자가점검 (<details> 정답)  ## 시험 팁  ## 더 읽을거리
```
